# 流式回答

## 需求与逻辑

当前聊天要等模型生成完整回答后才显示内容，等待期间只能看到加载状态。本次改为边生成边显示，用户发送问题后，模型返回的文字逐步追加到同一条回答中，Markdown 和代码块随内容更新

第一次发送仍先创建会话，后端立即保存初始标题，再发送问题。会话继续使用自己绑定的模型和已保存的历史上下文，生成过程中不修改标题。用户正在查看最新内容时，页面自动跟随；向上翻阅历史时不强制滚动

完整回答生成并成功保存到 MySQL 后，页面才标记本轮完成。用户问题和模型回答仍作为一轮完整记录保存；生成中的片段只用于当前页面展示，不逐段写入数据库

生成失败或超时时，保留已显示的内容并标记“生成失败”，提供重试入口；这部分内容不会作为后续模型上下文。重试时清空本轮临时回答，复用原来的请求编号。若上次实际已经保存成功，则直接恢复保存的问答，避免重复调用模型和重复入库

“停止等待回答”改为“停止生成”。点击后前端关闭当前流连接，后端检测到断开后取消本次图执行、关闭上游流并释放自己的会话占用。未完成的内容留在当前页面并标记“已停止”，不保存为历史消息。如果点击停止时数据库已经提交成功，则以已保存的结果为准，前端查询后恢复完整问答

停止后，页面先确认服务端已释放占用，再恢复发送按钮。同一会话仍只允许一个生成请求；切换会话只切换显示，正在生成的回答继续更新原会话。刷新或关闭页面会断开流，重新打开后读取数据库结果，生成中的临时片段不会恢复

## 技术方案

### 接口变动

新增 `POST /conversations/{id}/messages/stream`，前端聊天的发送和重试统一改用此接口，请求包含 `message`、`request_id`，成功建立连接后返回 SSE 事件流

浏览器调用地址为 `/api/conversations/{id}/messages/stream`，由 Vite 代理转发到后端

新接口请求示例，`request_id` 由前端为本轮生成 UUID，重试时复用：

```http
POST /conversations/{id}/messages/stream
Content-Type: application/json
Accept: text/event-stream

{"message":"Python 的异步怎么理解？","request_id":"72b23da8-f4af-4d12-9c01-f856f61a2258"}
```

### 流式返回格式

成功建立流时使用 `Content-Type: text/event-stream` 和 `Cache-Control: no-store`，每个事件由 `event`、JSON 格式的 `data` 和结尾空行组成

| 事件 | 数据 | 前端处理 |
|---|---|---|
| `delta` | `request_id`、`text` | 把本次新增文字追加到对应回答，`text` 不是累计全文 |
| `done` | `request_id`、`conversation_id`、`updated_at`、`generating: false`、`messages` | 数据已提交成功；`messages` 只包含本轮两条已保存消息，字段沿用现有 `MessageInfo`，替换本轮临时问答 |
| `error` | `request_id`、`code`、`message` | 终止本轮等待，标记错误并提供重试；提示不包含密钥或数据库内部信息 |

例如模型先返回“异步”，再返回“可以理解为……”：

```text
event: delta
data: {"request_id":"72b23da8-f4af-4d12-9c01-f856f61a2258","text":"异步"}

event: delta
data: {"request_id":"72b23da8-f4af-4d12-9c01-f856f61a2258","text":"可以理解为……"}

```

正常结束时发送一次 `done` 后关闭连接；发生错误时发送一次 `error` 后关闭连接。约 15 秒没有事件时发送 SSE 注释 `: ping` 作为心跳，前端忽略心跳。直接断开且没有收到 `done` 或 `error`，不能视为回答成功

请求参数、个人资料、会话归属、模型配置、重复请求和生成占用在建立流前检查，失败仍返回普通 HTTP 错误与 `{"detail":"提示"}`：参数错误为 422，会话不存在为 404，会话占用或请求编号冲突为 409，个人资料未初始化为 409，模型配置不可用为 503，数据库不可用为 503。流已经开始后不能再修改 HTTP 状态，模型失败、超时和保存失败改用 `error` 事件，`code` 分别为 `model_error`、`timeout`、`save_error`；本次占用已被后续请求替换时，返回 `request_expired`

如果相同 `request_id` 已经保存成功且问题一致，直接用已保存回答发送一个 `delta`，随后发送 `done`，不再调用模型；问题不一致返回 409。相同会话仍在生成时也返回 409，不额外开启一次生成

### 后端处理

继续通过 LangGraph 执行模型节点，使用 `agent.astream(..., stream_mode="messages")` 接收模型消息片段，只转发 `model` 节点的文本片段。保留当前 LangChain 模型客户端和会话绑定模型的方式，直接转发真实模型输出，不把完整回答拆字模拟流式效果

API 层只注册流式路由，SSE 输出、心跳和断开清理集中在 `app/services/streaming.py`，通过继承 `StreamingResponse` 管理响应生命周期。会话业务放在 `app/services/conversations.py`，普通发送和流式发送共用领取占用、读取历史、重复请求检查、保存整轮问答和释放占用的逻辑，区别是调用图和返回数据的方式

处理顺序为：检查请求并领取占用 → 读取最近 20 轮、最多约 6 万字符的历史 → 提交事务并释放数据库连接 → 执行图并发送片段 → 加锁核对占用编号 → 保存完整问答并释放占用 → 提交成功后发送 `done`

复用现有 `active_request`、`busy_until` 和消息表，不增加表或字段。进入流之前结束依赖查询产生的事务，流式业务通过数据库会话工厂按需创建短会话、短事务，等待模型和发送片段期间不持有行锁或数据库连接。流式总时限继续使用现有 `max(10, LLM_TIMEOUT × 3)`，占用到期时间继续额外预留 30 秒

后端同时监听客户端断开，在等待首个片段时也能取消图执行。异常和断开统一进入清理逻辑，关闭图迭代器、取消上游请求，并通过独立的短数据库会话释放占用；清理操作需要避免被同一次取消打断，只能清除属于本次占用编号的状态。若数据库暂时不可用，仍由占用到期机制恢复，不能清除新请求的占用

保存结果和停止可能同时发生：保存事务尚未提交时取消并回滚；提交已经成功时保留完整问答，不能因为页面未收到 `done` 再删除记录

### 前端处理

在 `frontend/src/api.ts` 中增加流式请求与事件读取逻辑，使用 `fetch` 发送 POST，通过 `ReadableStream` 持续读取。解析器用流式 UTF-8 解码，并保留未读完的事件缓冲，处理一个事件跨多次网络读取、一次读取包含多个事件和换行分隔的情况

`App.tsx` 根据会话编号和请求编号更新对应回答，收到 `delta` 后追加文字；收到 `done` 后只合并本轮消息、生成状态和更新时间，保留当前标题、模型信息及其他历史消息，避免旧响应覆盖页面上的会话资料。自动滚动沿用现有的跟随判断

`AbortController` 用于停止当前流，界面先显示停止中。收到错误、主动停止或连接异常中断后，通过现有详情接口核对结果：若找到本轮 `request_id`，恢复已保存问答；若仍为生成中则继续查询；确认占用已释放且没有保存本轮时，保留失败或停止状态并允许重试。新的请求使用新编号，重试沿用原编号，不自动重连后重复生成

当前 Vite `/api` 代理继续使用，联调时确认它逐段转发 SSE；后续接入其他反向代理时，流式路径需要关闭响应缓冲，并使连接超时覆盖本轮生成时间
