# CQ Agent Assist 产品需求与技术方案

## 一、产品需求

### 1. 项目定位

CQ Agent Assist 是一个给自己使用的个人 Agent 助手。它先解决资料收集和查询问题，再逐步增加 Agent、MCP、插件、多模态和沙箱能力。

项目以本地运行和单用户使用为主，当前不考虑多租户、组织管理和复杂权限。

### 2. 要解决的问题

资料会来自 RSS、本地文件、网页、数据库或第三方接口。这些来源的格式各不相同，如果每种来源都直接写进业务代码，后面增加功能时会不断修改原有逻辑。

项目需要先把不同来源转换成统一文档，再用统一的方式保存、查询和使用这些文档。

### 3. 核心业务逻辑

```text
添加数据来源
    ↓
读取原始内容
    ↓
转换成统一文档
    ↓
保存正文和来源信息
    ↓
关键词或向量检索
    ↓
Agent 根据检索结果回答
```

RSS 只是第一种数据来源。以后接入文件、网页或第三方 API 时，只增加对应的来源实现，查询和 Agent 部分继续使用统一文档。

### 4. 主要需求

系统需要能够接入数据来源、同步内容、保存文档，并记录来源地址、标题、发布时间和原始标识，避免相同内容重复保存。

系统需要提供统一查询入口。查询结果要包含正文或摘要以及来源信息，方便后续生成回答和展示引用。

Agent 的第一步先通过 LangGraph 接收问题、调用模型并返回回答。之后再增加检索节点、来源引用、工具调用和多轮任务。

MCP 和插件都作为工具接入。Agent 只依赖统一的工具描述和执行接口，不直接依赖某一个 MCP 服务或插件实现。

文档未来可能包含图片、音频和视频，因此文档模型需要保留资源关联信息，后面再增加多模态处理和相似图片检索。

### 5. 实现顺序

第一步通过 LangGraph 跑通基础对话，模型服务可以通过配置切换。已有的文档对象和内存数据源保留到接入资料时使用。

第二步接入 RSS 和 MySQL，保存来源配置、文档元数据和同步记录。

第三步增加文本切分、向量生成和检索增强问答。

第四步接入 MCP、插件和任务编排。

第五步再考虑多模态资源和受限沙箱。

## 二、技术方案（初版）

### 1. 总体结构

项目采用分层结构：

```text
接口层       FastAPI 路由
应用层       同步、查询、问答等用例
领域层       Document、Source、Retriever、Tool 等协议
基础设施层   MySQL、向量库、RSS 客户端、模型客户端
```

接口层只负责接收请求和返回结果，具体业务放在应用层。领域层定义模块之间的约定，基础设施层负责连接外部系统。

### 2. 数据来源设计

所有来源都实现统一的数据来源协议，例如提供异步的 `load` 方法，返回统一的 `Document` 列表。

RSS、文件和网页分别放在独立模块中。这样新增一种来源时，不需要修改查询器和 Agent 的代码。

### 3. 文档模型

文档至少包含正文和元数据。正文用于清洗、切分和检索，元数据保存标题、来源地址、来源类型、发布时间、抓取时间和原始标识。

后续可以在文档上关联图片、音频、视频和向量信息，但不提前把这些功能写进当前 MVP。

### 4. 存储设计

MySQL 保存来源配置、文档元数据、同步记录和运行记录。文档正文可以先跟元数据一起保存，后续根据数据量决定是否拆分。

向量检索在真正实现 RAG 时再接入 Milvus。检索器使用协议隔离具体向量库，便于以后替换实现。

### 5. Agent 和工具设计

Agent 使用 LangGraph 管理消息状态和节点执行顺序，模型客户端由 LangChain 提供。先实现一个模型节点；检索和工具能力实现时，再加入对应节点及条件分支。

MCP 服务和自定义插件都转换成统一工具，Agent 不需要分别处理不同工具的通信细节。

沙箱属于独立的执行模块，后续通过权限、超时和资源限制控制风险，不放入当前基础版本。

### 6. 当前技术栈

- Python 3.11
- FastAPI
- LangGraph
- LangChain 模型客户端（当前通过百炼兼容协议调用）
- Pydantic Settings
- MySQL
- SQLAlchemy 异步访问
- Milvus（实现向量检索时接入）
- Conda 管理本地环境

当前先完成单轮对话，真正需要持久化和向量检索时再接入对应基础设施。
